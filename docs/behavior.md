# Auto-Concur 동작 명세와 C단계 구조

## 유지하는 사용자 흐름

A 전표 다운로드 → B 파싱·입력 데이터 생성 → 작업지 편집 → C 반영.
SSO·카드 인증과 대상 리포트 선택은 사용자가 수행한다. A·B의 기존 처리와
숙박 입력·참석자 동기화의 기존 UI 조작 순서는 유지한다.

## 입력 정책

- 미입력 칸은 현재 Concur 값을 유지한다. 설정 기본값을 자동 주입하지 않는다.
- 대중교통비는 설명(코멘트)만 변경한다. 이전 목적·참석자 값이 있어도 입력하지 않는다.
- 식음료 참석자는 명시한 참석자와 추가 참석자를 기존 규칙대로 합친다.
- 숙박은 명시한 날짜·위치·예약 채널만 변경한다. 날짜가 없으면 객실 요금을 새로 입력하지 않는다.
- 기존 숙박 명세를 무조건 지우거나 다시 생성하지 않는다.
- 영수증이 있는 경비는 유지하고, 없는 경비에만 첨부한다. `--again`에서도 불명확한 첨부를 강제 중복 전송하지 않는다.
- 거래일·금액·가맹점 등 원본 식별 정보는 편집·교체 대상에서 제외한다.
- 유형별 입력 안내색과 실행 정책은 `expense_policy.py`에서 관리한다.

## C단계의 경계

1. 파일 사전 확인: 파일을 읽지 못하면 브라우저를 열기 전에 중단한다.
2. `report_session`: Concur 리포트 목록 주소와 전체 관측 목록의 안정성을 연속 확인한다.
   안정된 행에 값이 없어도 보존하여 대상별 매칭 단계에 넘긴다.
   로그인 화면, 경비 상세 화면, 일부 행만 준비된 화면은 시작 확인을 띄우지 않는다.
   10분 내 준비되지 않거나 브라우저를 닫으면 중단한다. 빈 리포트도 시작 대상으로 인식하지 않는다.
3. `concur_workflow`: 한 번 읽은 목록으로 영수증·입력 작업 계획을 만든다. 영수증과 입력 원본을 통합하여 대상별로 매칭한다.
4. 사용자에게 제목·리포트 ID·건수와 `이 리포트에 반영 시작` / `취소`를 제시한다.
5. 시작 시 주소와 목록을 다시 비교한다. 대상이나 목록이 바뀌면 쓰기 없이 중단한다.
6. `execution`: 작업별 실행 전 조회 → 작업 기록 → 실행 → 다시 조회 → 결과 기록.
7. `concur_driver`: 기존 UI 동작과 새 저장 결과 조회를 연결한다. 다른 리포트나 로그인 화면에서는 중단한다.

`--apply` 없는 미리보기는 Concur·진행 기록을 변경하지 않는다. `--limit`은
영수증과 입력 각각의 앞 N건에 적용된다. 시작 취소는 아무것도 반영하지 않는다.
기존 개별 CLI `attach_receipts` / `fix_expenses`는 호환을 위해 남아 있으며,
새 계획·진행 기록은 GUI C 및 `update_concur` 경로에 적용된다.

## 대상별 매칭 정책

`target_matching.py`가 GUI C/통합 CLI의 영수증·입력 계획에 같은 매칭을 제공한다.
개별 CLI도 동일한 보수적 매칭 함수를 사용한다. 목록에서 불완전 행을 먼저 제거하지 않는다.

| 관측 근거 | 처리 |
|---|---|
| 읽힌 날짜가 허용 오차 밖이거나 금액이 다름 | 해당 원본 거래와 무관한 후보로 제외 |
| 모든 원본과 위 조건으로 불일치 | 대상 무관 경비로 표시, Concur 값/영수증은 유지 |
| 관련 가능한 행에 날짜·금액·ID 누락 또는 ID 중복 | 해당 원본 거래를 보류, 다른 안전한 거래 계속 |
| 날짜와 금액 모두 미확인 | 어느 원본과도 무관하다고 단정하지 않음; 모든 대상 보류 가능 |
| 여러 완전 후보 | 기존 가맹점 판별 기준으로 유일하게 구별되면 선택, 아니면 보류 |
| 여러 원본이 같은 경비 후보를 공유 | 선착순 배정 없이 해당 원본 모두 보류 |
| 목록 로딩 또는 알려진 전체 행 수 미충족 | 개별 행 문제가 아니므로 목록 처리 차단 |

영수증과 작업지는 승인번호·날짜·금액·가맹점이 같고 각 소스에서 하나씩 있을 때만
동일 대상으로 합친다. 한 소스 안의 중복 또는 승인번호 없는 거래는 임의 합치지 않는다.
`--limit`은 매칭 판정 후 적용하므로 앞 N건 제한으로 충돌 검사를 우회하지 못한다.
수동 생성 여부/오류 아이콘/영수증 존재 여부는 대상 무관의 근거가 아니다.

시작 확인에서는 원문을 포함한 목록을 다시 비교한다. C단계 실행 전·후 조회에서도
대상 매칭을 재평가하고 연결이 모호해지면 해당 작업을 기록 후 보류한다.
일부만 처리한 결과는 전체 완료로 표시하지 않고, 원본별 보류 이유와 미해결 건수를 출력한다.
제외는 프로그램의 작업 대상에서 빼는 뜻이며 Concur 경비 삭제가 아니다.

## 기록과 재개

전표 폴더의 `concur-progress.json`에 리포트·경비·작업 종류·입력 내용 해시로
작업을 식별한다. 실제 문구가 포함될 수 있어 Git에서 제외한다.

| 상태 | 의미 | 다음 실행 |
|---|---|---|
| pending | 쓰기 전 화면 조회를 확정하지 못함 | 다시 조회 후 판단 |
| running | 쓰기 직전 기록됨, 종료 기록 없음 | 결과부터 조회, 자동 재전송 금지 |
| verified | 새로 연 화면에서 결과 확인 | 다시 확인 후 이미 반영됐으면 유지 |
| needs_review | 실행 뒤 결과를 확정하지 못함 | 결과가 확인되면 완료, 그 외 직접 확인 |

완료 기록만으로 작업을 건너뛰지 않는다. 현재 화면이 기준이다. 저장 중 오류가
나도 새 조회에서 목표 값이 확인되면 완료로 기록한다. 조회 실패와 저장 실패를
동일한 것으로 취급하지 않는다. 진행 기록을 저장할 수 없으면 쓰기 작업을 시작하지 않는다.

진행 기록은 영수증 첨부와 경비 입력 단위다. 숙박 내부의 개별 클릭 단위 재개는
지원하지 않는다. 불명확한 건은 Concur에서 결과를 직접 확인·수정한 뒤 C를 다시
실행한다. 기록 파일을 지워 일괄 재전송하는 방법은 정상 복구 절차가 아니다.

## 저장 검증과 한계

- 사용자 실행 로그에서 영수증 첨부와 일반 경비 입력의 저장 확인을 확인했다.
  호텔 실제 테스트 사례는 아직 없어 숙박 명세의 실제 저장·재조회 검증은 대기 중이다.
  실제 환경의 중단 후 재개와 단독 EXE 빌드도 추가 검증이 필요하다.
- Concur에 아직 도착하지 않은 거래는 `매칭 미해결`로 남긴다. 동일 거래가
  첨부·입력 양쪽에서 미해결이어도 한 거래로 집계하고, 저장 실패와 구분해 안내한다.
  경비가 올라오면 A·B를 반복하지 않고 C단계에서 다시 매칭할 수 있다.
- 영수증: 목록을 새로 읽어 해당 경비 ID·날짜·금액과 영수증 파일 이름을 확인한다.
- 일반 입력: 상세를 새로 열어 목적·설명·유형을 계획과 비교한다.
- 참석자: 새 참석자 화면에서 이름 목록을 조회한다. 검증 중 저장하지 않는다.
- 숙박: 날짜·위치·채널과 읽을 수 있는 객실 요금 입력값을 비교한다.
  기존 명세 표의 날짜·금액을 구조적으로 읽을 근거가 없는 화면은 `확인 필요`로
  남긴다. 표의 존재만으로 숙박 명세가 맞다고 판정하지 않는다.
- 일부 필드가 아직 렌더링되지 않았으면 확인 필요가 될 수 있다. 실제 Concur
  화면을 통한 추가 검증이 필요하며, 합성 화면 테스트 통과가 실제 서비스 보장은 아니다.
- 같은 날짜·금액 후보의 순서 배정은 금지한다. 가맹점으로 구별할 수 없으면 관련 거래를 보류한다.

## 찾기·바꾸기

Ctrl+H 또는 도구막대에서 연다. 다음 찾기·현재 셀 바꾸기·모두 바꾸기를 제공한다.
정규식이 아닌 입력한 문자열 그대로 검색한다. 대소문자 구분·셀 전체 일치를 선택할 수 있다.
현재 표시 행이 기본 범위이며 전체 행과 개별 입력 열을 선택할 수 있다.
모두 바꾸기는 대상 셀 수와 변경 내용을 확인한 뒤 하나의 실행 취소 작업으로 적용한다.
빈 문자열로 교체할 수 있으며 빈 검색어는 허용하지 않는다. 저장 전 유효성 검사는
기존 편집과 동일하게 적용한다.
