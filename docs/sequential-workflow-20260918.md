# C단계 — 경비 한 건씩 상세 확인 후 처리

## 처리 순서

리포트 목록을 열고 시작을 확인하면 경비 ID를 방문 순서로 고정한다.
각 ID의 상세 화면을 열어 거래 날짜·금액·가맹점을 읽고 작업지/전표에서 일치 거래를 찾는다.
번호 순서로 원본을 배정하지 않는다. 날짜·금액 정확 일치를 우선하고 없을 때만 기존 설정의
날짜 허용 오차를 사용한다. 여러 원본이 같은 후보이면 가맹점으로 구별하고, 구별하지 못하면 그 건만 보류한다.

- 일치 거래가 없으면 Concur 입력/첨부/저장을 하지 않고 다음 경비를 조회한다.
- ID 누락·중복이나 상세 읽기 실패는 해당 경비를 보류하며 다른 경비를 계속 확인한다.
- 목록에서 실제로 확인된 동일 후보와 이미 같은 원본을 처리한 다른 경비 ID는 임의로 선점하지 않는다.
- 목록에서 날짜·금액을 못 읽은 행을 모든 거래의 경쟁 후보로 취급하지 않는다.
- 알려진 `data-testid="footer-columns"`는 합계 영역이므로 경비에서 제외한다. 마지막 행 자체를 버리지 않는다.
- 리포트/로그인이 바뀌면 전체 실행을 중단한다. 경비별 실패와 다르다.

## 영수증과 입력

각 경비의 필요한 첨부/입력 작업을 수행하고 저장 결과를 확인한 뒤 다음 ID로 넘어간다.
기존 영수증은 파일 이름과 무관하게 유지하며 PDF를 추가 업로드하지 않는다.
조회 후 다른 영수증이 생기거나 상태가 모호해도 덮어쓰지 않는다.
새 업로드는 기존 파일이 없다는 확인 후에만 하고, 업로드 후 파일명/영수증 상태를 다시 검사한다.

목록은 ID 방문 순서, 해당 ID의 영수증 상태 및 실제 중복 후보 확인에 사용한다.
날짜·금액·가맹점은 상세 화면을 기준으로 읽으며 모든 목록 행의 완전한 해석을 선행 조건으로 삼지 않는다.
저장 검증을 위해 같은 경비의 상세/목록을 다시 조회할 수 있다. 경비당 브라우저 이동이 한 번뿐이라는 뜻은 아니다.
설명 전용 유형, 식음료 참석자, 숙박 입력 등 기존 작성 규칙은 그대로 사용한다.
빈칸은 기존 Concur 값 유지이며 신규 경비/마일리지 생성 및 리포트 제출은 하지 않는다.

## 기록과 재시작

기존 `concur-progress.json`의 첨부/입력 작업 키를 유지한다. 경비 ID와 원본 연결의 기록을 추가한다.
실행 전/후 확인과 미확정 작업 재전송 방지는 기존 실행기를 사용한다.
이전 실행이 중단됐더라도 현재 결과를 확인하지 않고 완료 처리하지 않는다.
원본 한 건을 다른 경비 ID에 다시 연결하지 않는다. 이전 연결이 필요 없어졌다면 별도 확인 대상이다.
미확정 첨부 쓰기 후에는 같은 경비의 다른 저장을 이어 하지 않고 그 건을 보류한다.
모든 기록/초기 파일 읽기는 기존 형식을 사용한다. 이 변경 때문에 작업지나 진행 기록을 삭제하지 않는다.

시작 확인은 리포트와 방문/원본 건수를 보여준다. 실제 첨부/수정 건수는 상세 조회 후 결정한다.
`--limit`은 기존처럼 첨부와 입력 각각의 최대 건수다. 남은 건은 제한으로 구분한다.
한 건씩 처리 모드의 `--again`은 허용하지 않는다. 기존 영수증을 보존하는 실행만 지원한다.
미리보기는 상세를 읽지만 Concur 쓰기 및 진행 기록 저장을 하지 않는다.

## 범위와 검증

기본 GUI/CLI C단계는 `sequential_workflow`를 사용한다. 기존 별도 CLI 첨부/수정 모듈은 유지한다.
한글 입력/참석자 LOV/마일리지 UI는 이번 수정에 포함하지 않는다.
목록에 아직 로드되지 않은 다른 페이지를 자동 조사하는 기능은 추가하지 않았다.
조회 범위에서 찾지 못한 원본 거래는 최종 미연결 건수에 남긴다.
상세에서도 필드/날짜 서식을 확인할 수 없으면 해당 경비를 보류한다. 외화를 원화로 추측하지 않는다.

합성 화면/거래 테스트: footer 제외와 실제 마지막 경비 보존, 상세 날짜 서식·통화,
지연/숨겨진/중복 입력칸, 한 건 완료 후 다음 ID 방문, 기존 영수증 유지, 미리보기/취소,
실제 중복, 재실행, 미확정 업로드, 원본 연결 기록, 리포트 변경 차단.
Windows EXE 빌드 및 실제 계정의 경비 저장은 이번 검증에 포함하지 않는다.
