# Auto-Concur

현대카드 전표를 정리하고, 프로그램 안에서 경비 정보를 입력한 뒤 Concur에 반영합니다.
**Excel 앱이나 엑셀 파일을 사용하지 않아도 전체 작업을 진행할 수 있습니다.**

## 2026-09-17: 대상별 제외와 보류

C단계는 안정된 목록에서 **대상과 무관한 경비는 그대로 두고, 애매한 거래만 보류**합니다.
- 날짜 또는 금액 중 읽힌 값이 원본 거래와 불일치하면 그 거래의 후보에서 제외합니다.
- 날짜·금액·ID를 못 읽은 행도 버리지 않습니다. 관련 가능성이 남은 원본 거래만 보류합니다.
- 날짜와 금액을 모두 못 읽으면 무관함을 입증할 수 없어 여러 거래 또는 전부가 보류될 수 있습니다.
- 수동 생성, 오류 아이콘, 영수증 유무만으로 제외하지 않습니다.
- 동일 날짜·금액 후보의 순서 배정을 없앴습니다. 가맹점으로도 구별되지 않거나 여러 원본이 같은 경비를 가리키면 보류합니다.
- 영수증과 작업지를 함께 매칭합니다. 시작 확인 후와 각 작업의 조회 시점에 대상 연결을 다시 확인합니다.
- 목록 로딩 중, 알려진 전체 행 수보다 적은 화면, 리포트 변경은 여전히 안전을 위해 차단합니다.

조회 시작·종료일은 첫 화면 달력으로, 작업지 입실·퇴실일은 셀 더블클릭/Enter 또는 `숙박 날짜 · 달력`으로 선택합니다.
`거래일`은 원본 매칭 정보이므로 편집하지 않습니다.
Windows 단일 파일은 `setup.bat` 실행 후 `build_exe.bat`으로 `dist/Auto-Concur.exe`를 만듭니다.
새 코드를 받아도 기존 EXE는 바뀌지 않으므로 다시 빌드해야 합니다. 생성물/실제 Concur 검증 범위는 CI 기록을 확인합니다.

## 실행

Windows / Python 3.10 이상을 사용합니다.

1. 소스를 받은 폴더에서 `setup.bat`을 실행합니다. 기존 사용자도 새 표 라이브러리 설치를 위해 한 번 실행합니다.
2. `run.bat`을 실행합니다.
3. 기간과 전표 폴더를 선택합니다.
4. **A. 전표 다운로드** → **B. 파싱 · 작업지 생성** → **작업지 편집** 순서로 진행합니다.
5. 프로그램 표에 내용을 입력하고 **저장하고 Concur 반영**을 누릅니다.

카드 인증과 Concur 로그인·리포트 선택은 직접 합니다. 프로그램의 안내창에서 준비가 끝난 뒤 확인을 누릅니다.

C단계에서는 로그인 후 리포트 **목록**을 열면 프로그램이 준비 상태를 자동 확인합니다.
제목·리포트 ID·첨부/수정 건수가 표시된 뒤 **이 리포트에 반영 시작**을 누릅니다.
시작 전 화면이 바뀌면 중단하며, 저장 후에는 결과를 다시 읽어 확인합니다.
`확인 필요` 항목은 자동 재전송하지 않습니다. 상세 정책과 검증 한계는 [동작 명세](docs/behavior.md)를 참고하세요.

## 프로그램 표

- 전체 열을 항상 표시하고, 경비유형별 입력 안내 칸을 초록색으로 강조합니다.
- 대중교통비는 코멘트(설명)만 반영합니다. 작업지에 기존 비즈니스 목적이 있어도 해당 칸을 찾거나 입력하지 않습니다.
- 제목 표시줄 또는 ‘경비 입력’ 제목을 더블클릭하면 최대화·복원합니다. 글자 크기는 10~14pt로 선택합니다.
- 셀 더블클릭 또는 키 입력으로 편집합니다.
- **찾기·바꾸기 / Ctrl+H**: 다음 찾기, 바꾸기, 모두 바꾸기. 현재 표시 행 또는 전체 행, 개별 입력 열을 선택할 수 있습니다. 모두 바꾸기도 Ctrl+Z로 한 번에 되돌립니다.
- 셀 범위 선택, Ctrl+C/V 복사·붙여넣기, Ctrl+Z/Y 실행 취소·다시 실행, Delete 비우기를 지원합니다.
- 경비유형·숙박위치·Booking Channel 드롭다운을 제공합니다.
- **여러 행에 입력**으로 선택한 행에 같은 코멘트·참석자·유형 등을 넣을 수 있습니다.
- 검색과 숙박비·식음료·입력 상태 필터를 제공합니다. **필터는 표시만 바꾸며 C단계 처리 대상을 제한하지 않습니다.**
- 거래일·금액·가맹점과 내부 전표 연결 정보는 편집에서 보호합니다.
- 입력 중 임시 저장하며, 같은 원본의 임시본은 다음에 표를 열 때 복원합니다.
- **이전 저장 복원**은 직전 저장의 입력값을 초안으로 되돌립니다. 저장해야 실행 데이터에 반영됩니다.
- 외부에서 원본이 변경되면 덮어쓰기를 중단합니다. **다시 불러오기**로 현재 저장 데이터를 확인할 수 있습니다.
- 필요할 때만 엑셀/CSV/JSON 입력을 가져오거나 엑셀로 내보냅니다. 가져오기는 현재 전표와 승인번호·날짜·금액이 일치하는 입력에 사용합니다.

표의 **입력 있음 / 영수증만 / 입력 확인**은 입력 상태입니다. Concur 반영 성공 여부는 C단계 실행 로그에서 확인합니다.

## 빈칸과 영수증 처리

**빈칸은 Concur의 현재 값을 유지한다는 뜻입니다. 기존 값을 지우라는 뜻이 아닙니다.**

- 유형·목적·코멘트·참석자·숙박 정보는 입력한 필드만 반영합니다.
- 설정에 기본값이 있어도 C단계에서 빈칸을 자동으로 채우지 않습니다.
- 참석자와 추가 참석자가 모두 비면 기존 참석자를 유지합니다. 입력하면 두 칸의 이름을 합쳐 해당 식음료 경비의 참석자를 맞춥니다.
- 입실·퇴실 날짜 칸을 더블클릭하거나 행 선택 후 **숙박 날짜**를 누르면 달력에서 두 날짜를 선택하고 박수를 확인할 수 있습니다. 적용은 한 번에 실행 취소할 수 있습니다.
- 직접 입력/붙여넣기도 가능합니다: `2026-09-01`, `2026.9.1`, `20260901`, `9/1`, `9월 1일`. 저장 시 `YYYY-MM-DD`로 통일합니다. 연도가 없으면 거래 연도를 사용하므로 해를 넘기는 퇴실일은 연도를 명시하세요. 입실·퇴실은 둘 다 입력하거나 둘 다 비웁니다.
- 숙박 날짜가 비면 날짜·객실 요금을 바꾸지 않습니다. 숙박위치·Booking Channel만 입력할 수도 있습니다.
- 숙박 날짜를 입력한 경우 기존 로직대로 박수와 경비 금액에 맞춰 객실 요금 입력을 시도합니다. 기존 명세가 있거나 수정 불가인 경우는 자동으로 덮지 않습니다.
- 편집 필드가 전부 비어 있어도 영수증은 화면 상태에 따라 처리합니다. 이미 있으면 건너뛰고 없으면 첨부합니다.
- `attached.txt`는 참고 기록입니다. 이 기록만으로 현재 화면에 영수증이 있다고 판단하지 않습니다.

## 저장 파일

전표 폴더 안에 저장됩니다. 파일을 직접 편집할 필요는 없습니다.

| 파일 | 역할 |
|---|---|
| `workbook.json` | 프로그램 입력 원본, C단계가 우선 읽는 데이터 |
| `workbook.draft.json` | 아직 확정 저장하지 않은 임시 입력 |
| `workbook.previous.json` | 직전 저장의 복원본 |
| `concur-progress.json` | 리포트별 실행·결과 확인 기록, 자동 재전송 방지 |
| `manifest.csv` | B단계가 만든 전표 파일 목록, 첨부에 사용 |
| PDF/사진 | 실제로 첨부할 영수증 |

B단계를 다시 실행해도 저장된 프로그램 입력값을 보존합니다. 파싱 실패가 있으면 기존 입력 데이터를 덮지 않습니다. 기존 XLSX를 읽지 못했을 때 오래된 CSV 값으로 대체하여 덮어쓰던 동작도 중단합니다.

기존 사용자: `workbook.json`이 없으면 기존 `manifest.xlsx` 또는 `manifest.csv`를 열 수 있습니다. 프로그램에서 저장하면 전용 데이터로 전환합니다. 그 후에는 외부 엑셀 변경이 자동으로 반영되지 않으며 **가져오기**를 사용합니다. 계산되지 않은 엑셀 수식은 빈 값으로 읽힐 수 있으므로 가져온 내용을 확인합니다.

## Chromium 화면 안정화

- 브라우저 기본 언어는 한국어(`ko-KR`)입니다. Concur 계정 언어 설정에 따라 영어로 표시될 수 있습니다.
- `Save Expense` 저장 버튼을 지원하고, 경비유형 선택 결과는 실제 옵션 이름으로 확인합니다.
- ‘다른 항목을 업데이트하시겠습니까?’ 확인창에서는 ‘업데이트’를 눌러 현재 경비의 명세에도 변경을 적용합니다.
- 화면 재렌더링 중 버튼이 교체되면 클릭 전에 대상을 다시 찾습니다.
- 현재 보이는 대화상자/패널에서 버튼을 찾고, 숨겨진 입력 템플릿을 제외합니다.
- 저장 버튼이 뒤늦게 나타나거나 다른 요소에 가려진 경우 클릭 준비를 기다립니다.
- 실제 클릭 결과가 불명확하면 저장/추가 버튼을 무조건 다시 누르지 않습니다.
- 숙박비 객실 요금 행들이 나누어 그려져도 예상 행 수와 편집 가능 상태가 준비될 때까지 기다립니다.
- 경비 목록의 일부 행만 준비된 상태에서 매칭을 시작하지 않습니다.
- 화면 탐색 실패 시 `inspect-out/ui-날짜-시간.json`에 해당 단계·버튼·대화상자 정보를 남깁니다.

진단 파일에는 화면의 업무 문구가 포함될 수 있으므로 공유할 때 내용을 확인합니다. 실제 Concur UI 변경이 있는 경우 최신 진단으로 셀렉터와 상태 전환을 검증해야 합니다.

## 명령행

```text
python -m src.gui
python -m src.download_slips --from 2026.09.01 --to 2026.09.30
python -m src.organize ./downloads
python -m src.organize ./downloads --apply
python -m src.update_concur --dir ./downloads
python -m src.update_concur --dir ./downloads --apply --limit 1
```

`organize`의 기본은 파일을 변경하지 않는 미리보기입니다. Concur 명령도 기본은 계획 출력이며 `--apply`가 있어야 반영합니다. GUI의 C단계는 실제로 반영합니다. `--limit`은 각 단계에서 앞 N건씩 제한합니다.

영수증 사진은 `20260901-17000.jpg`처럼 날짜와 금액으로 이름을 지정합니다. 같은 날 같은 금액이면 `20260901-17000-2.jpg`처럼 구분 번호를 붙입니다. HEIC는 지원하지 않습니다.

브라우저는 Playwright Chromium → Edge → Chrome 순서입니다. 기존 `CONCUR_BROWSER` 환경변수로 선택할 수 있습니다. 브라우저만 바꾼다고 화면 전환 문제의 해결이 보장되는 것은 아닙니다.

## 조사: Concur가 실제로 주고받는 호출 (변경 없음)

```text
python -m src.record_calls
```

지금 C단계는 **화면에 그려진 글자를 읽고 그 위를 클릭합니다.** 그래서 날짜 표시 서식,
숨은 저장 버튼, 패널이 클릭을 가로채는 것 같은 표현 계층 문제가 전부 우리 문제가 됩니다.
한 계층 아래(화면이 쓰는 JSON 호출)로 내려갈 수 있는지 보려면 먼저 그 계층이 있는지
확인해야 하고, 이 도구가 그것만 확인합니다.

**아무것도 바꾸지 않습니다.** 호출을 재생하지도, 저장을 누르지도 않습니다. 평소처럼
손으로 작업하시면 그동안 오간 호출의 *모양* 만 적습니다. 단계마다 Enter를 누르면 기록에
표시가 들어가서 어느 호출이 어느 동작의 것인지 나중에 가를 수 있습니다.

**값은 적지 않습니다.** 기록은 페이지 안에서 모양으로 바뀐 뒤에 나오므로 실제 거래 값은
파일에 닿지 않습니다. 남는 것은 이런 모양입니다.

```json
{"method":"PUT","path":"/nui/expense/entry/{id}",
 "reqBody":{"transactionDate":"str:date-iso","transactionAmount":"int"}}
```

`transactionDate`가 `str:date-iso`인지 `str:date-slash`인지가 알아야 할 전부입니다.
가맹점명·금액·승인번호·참석자 이름은 `str:len9-32` 같은 길이 구간으로만 남습니다.
결과는 `inspect-out/calls-*.jsonl`에 떨어집니다(gitignore 됨).

**Concur는 GraphQL을 씁니다**(2026-11-05 실측: `www-eu2.api.concursolutions.com/spend-graphql/graphql`).
호출이 전부 한 주소로 가는 POST라서 경로는 아무것도 알려주지 않습니다. 무엇을 하는
호출인지는 `operationName`과 질의문에 있고 그 둘은 스키마(필드 이름)이지 거래 값이
아니므로 - 값은 `variables`로 따로 갑니다 - 그 둘만 그대로 남깁니다. 요약도 경로가
아니라 작전 이름으로 가릅니다. 질의문에 값이 인라인으로 박혀 오는 경우를 대비해
문자열·숫자 리터럴은 지웁니다.

평소 C단계와 같은 브라우저 프로필을 씁니다. 이미 로그인돼 있어 편하지만 **둘을 동시에
띄우면 Chromium이 프로필을 못 열고 죽습니다.** 하나씩 돌리세요.

## GraphQL 교차검증 (2026-11-05부터 켜져 있음)

C단계가 경비 목록을 읽을 때 **화면과 GraphQL을 둘 다 읽어 맞춰 봅니다.** 화면 읽기를
대체하지 않습니다.

| 상황 | 처리 |
|---|---|
| 양쪽이 같다 | 그 값을 씁니다 |
| **화면이 못 읽었고 GraphQL은 읽었다** | **GraphQL 값을 씁니다** (전에는 보류됐던 경우) |
| GraphQL이 없거나 실패 | 화면 값을 씁니다 (= 이전 동작) |
| **양쪽이 다른 값을 말한다** | **값을 비웁니다 → 그 거래만 보류됩니다** |

마지막 줄이 핵심입니다. 어긋나면 어느 쪽도 고르지 않습니다. 값을 비우면 기존
대상별 보류가 그 거래만 붙잡으므로 **화면 혼자 결정하던 이전보다 보수적입니다.**

실행 중에 이런 줄이 보입니다:

```text
  (GraphQL이 화면의 빈 값 3건을 채웠습니다: 02FD45A7 날짜, ...)
  (두 경로가 어긋난 1건은 값을 비웠습니다 — 해당 거래만 보류됩니다)
```

끄려면 `AUTO_CONCUR_NO_GRAPHQL=1`. 보완이 본 작업을 막지 않도록, 어떤 예외도
올려보내지 않고 화면 값으로 넘어갑니다.

### 저장·첨부도 GraphQL로 갑니다 (2026-11-05부터)

| 작업 | 경로 |
|---|---|
| **비즈니스 목적 / 코멘트 저장** | GraphQL `UpdateExistingExpenseEntry` |
| **경비유형 변경** | GraphQL (같은 mutation의 `fields.expenseTypeId`) |
| **영수증 첨부** | GraphQL `upload` → `AttachImage` |
| 참석자 | 화면 (참석자별 `versionNumber`와 금액 분배 규칙이 아직 없습니다) |
| 숙박 항목별 명세 | 화면 (`roomRateExpenseTypeId`의 출처가 아직 없습니다) |

유형 변경에 `policyId`는 필요 없습니다. 그걸 쓰던 `CDS_addRecentExpenseTypes`를 우리
문서에서 뺐기 때문입니다. 저장소가 이미 들고 있는 코드(`PARKG`·`01143`·`LODNG`)가
실측된 `expenseTypeId` 모양과 같고, 저장 뒤 `verify_edit`가 화면에서 유형을 다시 읽어
대조하므로 독립 확인이 남아 있습니다.

**보내기 전에 검증합니다.** 같은 문서·같은 변수를 `@skip(if: true)`로 한 번 보내면
문서와 변수는 검증되고 resolver는 실행되지 않습니다. 즉 쓰지 않고 모양만 확인합니다.

**실패했을 때 되돌아가지 않습니다.** 보내기 전에 막힌 것과 보낸 뒤 결과를 모르는 것을
구분합니다. 전자는 화면 경로로 넘어가고, 후자는 **재시도도 폴백도 하지 않고** 그 경비만
실패로 남깁니다 — 둘 다 이중 저장이 됩니다. `concur_ui.click_target`이 "클릭 결과를
확인할 수 없으면 재클릭하지 않는다"로 이미 같은 판단을 하고 있습니다.

**저장 응답이 Concur 예외를 같이 줍니다.** `유효한 정보를 제공해야 합니다` 류가
구조화돼서 오므로 안내창 글자를 읽지 않습니다. 빈 필드 이름도 같이 옵니다.

끄려면 `AUTO_CONCUR_NO_GRAPHQL=1` — 읽기 보완과 같은 스위치입니다.

### 남은 둘: 쓰지 않고 모양만 시험합니다

```text
python -m src.probe_fields
```

**이 서버는 introspection이 막혀 있습니다**(2026-11-05 실측: 아는 작전 이름으로 같은
내용을 보내도 같은 400이라 거부 대상은 이름이 아니라 `__type`입니다). 그래서
`python -m src.inspect_schema`로는 스키마를 물을 수 없습니다.

그런데 알고 싶은 건 하나뿐입니다 — **어떤 필드가 필수인가.** 그건 묻지 않아도 알 수
있습니다. `@skip(if: true)`로 보내면 **변수 검사는 하고 resolver는 실행하지 않습니다.**
필드를 하나씩 빼서 보내 보면 어느 것이 필수인지 드러나고, **아무것도 쓰이지 않습니다.**

`transactionAmount`가 선택이면 안 보내고 Concur가 나누게 두면 되므로 분배 규칙을 알
필요가 없어집니다. 필수면 그때 따로 확인해야 합니다.

"통과"는 그 모양이 **검증을 지난다**는 뜻이지 업무 규칙까지 맞다는 뜻은 아닙니다.

## 읽기 비교만 따로 보기 (변경 없음)

```text
python -m src.compare_rows
```

경비 목록을 **화면과 GraphQL로 둘 다 읽어 비교만** 합니다. 지금은 옮기지 않고 잽니다.
둘이 한동안 일치하는 것을 본 뒤에 코드가 GraphQL 쪽을 쓰게 하고, 그때도 화면 경로는
폴백으로 남깁니다. **어긋나면 화면 쪽을 믿습니다** — 지금 돌고 있는 것이 그쪽이고
새로 붙인 쪽이 틀렸을 가능성이 더 큽니다. 그래서 이 도구는 판정하지 않고 차이를 적습니다.

저장·첨부·주문을 하지 않습니다. GraphQL 호출은 질의(query)뿐이고 mutation 은 부르지
않습니다 — 테스트로 강제합니다. 결과는 `inspect-out/compare-*.json`에 떨어집니다.

권한은 새로 생기지 않습니다. `browser.launch` 가 준 컨텍스트의 `request` 가 그
컨텍스트의 쿠키로 나가므로, **사람이 SSO로 로그인한 그 세션**을 그대로 씁니다.
그 가정은 실제 Chromium으로 검증합니다(`tests/test_graphql_session.py`).

## 테스트와 배포

```text
python -m pytest -q
```

화면 테스트는 서비스에 로그인하지 않고 Chromium의 합성 HTML에서 실행합니다. 설치된 Chromium 실행 파일은 `AUTO_CONCUR_TEST_BROWSER` 환경변수로 지정할 수 있습니다. 브라우저가 없으면 해당 테스트는 건너뜁니다. GUI 표 테스트에는 Tk가 있는 데스크톱 환경이 필요합니다. 실제 전표 PDF fixture가 없으면 파서 회귀 테스트 6개를 건너뜁니다.

`build_exe.bat`은 PyInstaller 단일 실행파일을 만들고, `make_exe.bat`은 현재 폴더의 venv를 실행하는 작은 C# 런처를 만듭니다. 후자는 폴더 전체가 필요합니다. 두 배포 방식은 별도 빌드 검증이 필요합니다.

코드는 다음 역할로 나뉩니다: `worksheet.py`는 입력 데이터와 저장, `worksheet_editor.py`는 표 UI, `concur_ui.py`는 화면 대기/클릭/진단, 기존 A/B/C 모듈은 다운로드·정리·Concur 반영입니다.
